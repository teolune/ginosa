## Implementation notes (engineering choices, no approval needed)

- **Time** is stored as integer ticks at 254,016,000,000 per second (Premiere's rate). See `src/engine/time.ts`.
- **Local media** is served to the renderer through a read-only `ginosa-media://` protocol with HTTP range support. Mediabunny reads files in pieces rather than loading them whole.
- **M0 UI** is plain DOM on purpose. It is a diagnostics shell, replaced by the real workspace in M1.
- **Media files** are identified by a fingerprint: size, modification time, and a SHA-1 of the first and last MiB. A file that changes size shows as *Changed*; a missing one shows as *Offline*.
- **Optimised copies** (M2): H.264 CRF 16 for 8-bit sources, HEVC Main10 via VideoToolbox for 10-bit and all HDR sources, keyframes every 0.5 s, 24-bit PCM audio, in `.mov`. Made automatically only when needed (codec not decodable by WebCodecs, variable frame rate); offered for keyframes more than 2 s apart. HDR copies keep their BT.2020 + HLG/PQ labels, stamped into the bitstream because Apple's encoder drops them. File names carry a format version (now v2), so changing the recipe never reuses stale copies.
- **HDR to Rec.709** maths lives in `src/shared/colour/hdr-to-sdr.ts`, ready for M4: HLG inverse OETF + OOTF at 1000 nits (PQ via its EOTF), 203-nit reference white mapped to 1.0, a soft roll-off above 0.75, BT.2020→709 matrix, then BT.709 gamma, generated as a 33³ `.cube`. Until M4, the Source Monitor shows HDR clips with Chromium's own conversion.
- **Cache** lives at `~/Movies/ginosa Cache/<project id>/<category>/` with an `index.json` naming each project. Every delete goes through `CacheService`, which checks the project ID and category, resolves real paths, stays inside the cache root and refuses symlinks. A chosen location always gets its own `ginosa Cache` subfolder.
- **Timeline edits** (M3) live in `src/engine/timeline/`. Each edit has a pure `apply…` function used both for the live drag preview and by its command, so the preview is the edit. Every position sits on the sequence's frame grid, so the frame rate is locked once clips exist.
- **Clips** store `start`, `duration` and `sourceIn` in ticks, plus a `linkId` shared by linked picture and sound. Splitting keeps the left half's link and gives the right halves a new shared one.
- **Defaults** taken from Premiere: stills last 5 s; a drag overwrites and Cmd-drag inserts; Option-drag copies; picture and linked sound mirror around the middle when moved between tracks.
- **Snapping** targets: the playhead, clip edges, markers and the sequence start, within 8 px. The playhead snaps while snapping is on, or while Shift is held.
- **Typed timecode** reads Premiere's forms ("1:02:03:04", "1000" read right to left, "+10" relative). Display is non-drop-frame only.
- **Playback clock** (M4): Web Audio's clock minus its reported output latency is the master; the picture follows a smoothed version of it (re-locked if the two ever differ by 50 ms) and never steps backwards. `getOutputTimestamp()` proved unreliable here, so it isn't used.
- **Media time 0** is the file's first timestamp, but never below 0. AAC audio often starts a few ms early (encoder priming), and anchoring on that put every video frame one frame late; the sync test caught it.
- **Compositor**: each layer is one full-frame pass that reads the layers below and writes into the other of two `rgba16float` textures. Video frames arrive as external textures (no copies); stills are uploaded once.
- **Colour on the Mac** (M4): Chromium converts decoded Rec.709 frames for the display (a 1.961 gamma to sRGB) before ginosa sees them. ginosa undoes that on the GPU, so effects and blends work on the file's own values, and applies it once at the monitor. Measured round trip: within 0.008 of the file's values.
- **Apple Log** (M4): iPhone log files carry no transfer tag, so ginosa asks the decoder for plain BT.709 Y′CbCr→RGB and gets the raw log values. Built-in conversion: Apple Log curve → linear, gamut (BT.2020 for Apple Log, Apple Wide Gamut for Apple Log 2) → Rec.709, a soft shoulder above 0.5, then the Rec.709 curve. Detection: 10-bit, BT.2020 matrix, unspecified transfer; primaries BT.2020 → Apple Log, unspecified → Apple Log 2. Confirmed on your clips (`Reference Materials/AppleLogClips`): HEVC Rext 4:2:2 10-bit, 3840×2160, 25 fps, keyframes every 1 s; container `colr` and SPS VUI both 9/2/9 (Apple Log) and 2/2/9 (Apple Log 2). Chromium decodes 4:2:2 HEVC in hardware on your M5: both clips played at 25 fps with 0 dropped on a 1080p timeline, so they need no optimised copy. Checked by `npm run snapshot -- --scenario footage` (and `footage2`).
- **HDR** (M4): Chromium tone-maps HLG/PQ frames itself and ignores the decoder colour request for them. So as an HLG/PQ HEVC file is read, ginosa rewrites the 8-bit `transfer_characteristics` in its SPS (in the `hvcC` header and in any SPS repeated inside packets) to "unspecified" (`src/engine/colour/hevc-sps.ts`). Frames then arrive raw, as Apple Log does, and the shader applies the maths in `src/shared/colour/hdr-to-sdr.ts` exactly. The parser follows H.265 §7.3.2.2 and matches FFmpeg's bit positions on x265, VideoToolbox and a hand-built SPS covering every branch. Non-HEVC HDR (rare) still gets Chromium's conversion. Measured: within 0.011 (HLG) and 0.02 (PQ) of the maths, all of it on the brightest test patch where the test file's 10-bit rounding is amplified.
- **Speed and reverse** (M4): a clip at speed *s* covers `duration × s` of its media. A reversed clip shows exactly the frames it shows forwards, in the opposite order. Reverse playback decodes ~0.3 s stretches latest-first (keeping at most 8 frames each) while the previous one plays.
- **Source Monitor** (M4): plays the open file as a one-clip sequence at the file's own size and frame rate (`src/engine/timeline/source-sequence.ts`), through the same player as the Program monitor: sound, colour conversion and the audio clock. Starting playback in one monitor stops the other. Mark Out includes the frame on screen, as in Premiere (stored as the end of that frame; the label shows the frame itself). Files at non-standard rates (e.g. 120 fps) play at the nearest standard rate or 25 fps.
- **Export** (M5): the renderer renders each frame with the same render plan, layer builder and compositor as playback, decoding exactly (no deadline). A compute pass (`yuv.wgsl`) converts the 16-bit float composite to BT.709 limited-range Y′CbCr with left-sited chroma and triangular dither, in the exact raw layout FFmpeg reads (NV12, P010, 4:2:2 or 4:4:4 10-bit). The sound is mixed offline by the playback mixer (`audio-mixdown.ts`). Main pipes both to FFmpeg: VideoToolbox for H.264/HEVC, `prores_ks` for ProRes, Rec.709 tags on input and output, `write_colr`. The file is written under a hidden name and renamed only on success.
- **Export checks** (`npm run export-test`, reading the files back with FFmpeg): A/V sync within 0.02 ms on all 10 flash/beep pairs; colour within about one code step of the preview (H.264 0.005, HEVC 10-bit 0.0011, ProRes 0.0009) with BT.709 tags; all 275 frames of the speed/reverse/hold/dissolve timeline exact in H.264 and ProRes. Speed on your Mac, 1080p: about 120 fps (H.264 from 1080p sources); your 4K Apple Log clips export at 66 fps (H.264) and 31 fps (ProRes 422 HQ). `prores_videotoolbox` (hardware ProRes) is a possible speed-up.
- **Effects** (M6): an effect is a folder in `src/effects/<id>/` with `manifest.ts` (parameters, colour space, version, `migrate`), `shader.wgsl` (`fn effect(px) -> vec4f`) and CPU reference maths for tests; `src/effects/registry.ts` finds them with `import.meta.glob`. `effect-shader.ts` wraps each shader: its parameters become a uniform struct (choices as indexes, points as `_x`/`_y`, pixel values scaled to the processing size), helpers read the input in the effect's colour space (display; linear light at gamma 2.4; OKLab), and the shared ending converts back and applies the blend mode and Mix. `blend.wgsl` holds all 24 modes (Photoshop formulas; Hue/Saturation/Color/Luminosity per W3C) and is shared with clip compositing.
- **Effect rendering** (M6): a clip with effects is drawn upright and colour-converted into a scratch texture at its own size, run through its effects, then placed by Motion. An adjustment layer runs its effects on the composite so far and blends the result back (`fsAdjust`). Scratch textures are pooled between frames. Missing effects (from a newer ginosa) are kept in the project and pass the picture through.
- **Keyframes** (M7) live in `src/engine/keyframes/`. A value's keyframes are a list sorted by time, in ticks from the clip's start (`Clip.keyframes` for Motion, Opacity, Volume and Speed; `EffectInstance.keyframes` for effect settings and `mix`). Each keyframe says how the value leaves it (hold, linear, bezier) and carries two handles: `t`, how far along its segment it reaches (0–1, so curves can never loop back in time), and `v`, value offsets per component. Bezier segments are solved for time by bisection (48 steps, exact to 1e-14 of a segment). Before the first keyframe and after the last the value holds. A value with keyframes ignores its stored value. Every edit snaps keyframes to the frame grid.
- **Resolving** (M7): the render plan hands each layer the clip as it is at that frame (`resolveClip`), with animated values worked out and clamped to their ranges (bezier overshoot can't push Opacity past 100%). Unanimated clips pass through untouched, so nothing else changed and older projects render exactly as before. Preview, still frames and export all go through it.
- **Speed ramps** (M7): a ramped clip's place in its media is `sourceIn + ∫ speed dt`. The integral is exact: linear segments are trapezoids, and a bezier segment is integrated in its curve parameter, where speed × dx/ds is a degree-5 polynomial, so 3-point Gauss–Legendre has no error. Trims move `sourceIn` by the integral and shift keyframes the other way, so every frame stays put; trim limits invert the integral by bisection. The done-when test checks every frame against an independent Simpson's-rule integration.
- **Linked sound on a ramp** (M7, decision 41): every timeline command ends by copying a ramped picture's Speed keyframes onto its linked sound (`syncLinkedRamps`), and removing them when the link or alignment is gone; opening a project rebuilds the copies. Each decoded piece of sound starts when the ramp reaches it (the inverse of the ramp's integral) and its Web Audio playback rate follows the ramp, sampled every millisecond. Live playback and the export mixdown share this code.
- **Volume keyframes** (M7) are in dB and interpolate in dB. The clip's gain node follows them as a Web Audio value curve sampled every millisecond (2 million points at most, so very long clips are sampled more coarsely), scheduled the same way by live playback and the export mixdown.
- **Keyframe Editor** (M7) is drawn on a canvas (`src/renderer/src/keyframes/editor-canvas.ts`). Drags preview through the timeline's preview sequence (so the Program monitor follows) using the same `apply…` functions as the commands, and commit one command when you let go.
- **Audio analysis** (M8) lives in `src/engine/audio/`. A source is mixed offline by the playback mixer (`renderAudio`, the same code as export's mixdown) to mono at 48 kHz, then analysed in a Web Worker (`analysis.worker.ts`). Filters run forwards then backwards (2nd-order Butterworth both ways = 4th-order Linkwitz–Riley, zero phase). Results are packed (a JSON header plus Float32 signals) into the project's `analysis` cache as `<key>.bin`, where the key hashes everything that changes the source's sound (files, positions, speed, volume) and the analysis version. Custom bands are cached the same way, keyed by range.
- **Tempo detection** (M8): onset = the sum of the band transients. Autocorrelation scored with a 4-harmonic comb and a log-normal preference around 120 BPM picks the tempo; then every onset is folded onto one beat's length (coarse 0.02 BPM, fine 0.001 BPM) and the tempo and phase where they pile up highest win. Hits are moved to the sharpest rise of the whole sound's 5 ms level within 40 ms, which put them within 0.1 ms of synthetic kicks.
- **Modulation** (M8) lives in `src/engine/modulation/`. Each modulator's output is computed for the whole sequence (plus 30 s) at 200 values a second (`modulatorCurve`); values between samples are linear. The renderer keeps the curves (`modulation-controller.ts`) and rebuilds one only when its modulator, its source's analysis or the beat grid changes. The render plan resolves keyframes, then links in order, then clamps (`resolveClip`). Export waits for analysis and renders from a fixed snapshot of the curves, which is why playback and export can't disagree.
